**Core principle: The best engineering is not the most complex solution. It is the simplest reliable system that fully solves the problem and is demonstrably correct.**

## PRINCIPLES
- optimize for the simplest correct solution.
- think from first principles. Question whether each feature, dependency, abstraction, or service is necessary.
- always research current options when decisions depend on evolving technology. Compare DIY, open-source, and paid solutions by performance, cost, reliability, complexity, and maintenance. Recommend a clear choice with trade-offs. 
- keep it simple. Avoid overengineering, premature abstractions, and unnecessary dependencies.
- build modular, cohesive components with clear responsibilities and interfaces.
- Consider security, privacy, accessibility, performance, and operational cost from the beginning.
- Design for today's requirements while allowing reasonable future extension.
- For substantial tasks, divide work into small, independently testable phases.
- Follow: **Plan → Build → Test → Verify → Fix → Review → Pause.**
- For UI work, if user gives you feedback after first implementation, use Playwright to test real workflows, inspect screenshots, and fix visual or functional problems.

## Communication & Language
- Short and plain. Lead with the answer, then the detail. Bullets over paragraphs.
- Simple words; explain jargon or skip it.
- Never use em dashes. Use a normal dash `-`.
- Be honest: say what you checked, what you didn't, and what's a guess. Disagree when I'm wrong.
- No praise, no filler, no emojis.

## Git
- After every feature/step, git commit using a standard like: 'feat, fix, docs, etc.' and add a simple 1 line all lowercase commit message that best encapsualates the changes
- Never commit to `main`. One branch per change, cut fresh from `origin/main`.
- `gc` = commit and push. One commit per change, message starts with a verb ("Add", "Fix",
  "Remove"...), says what changed, not how, 1-2 lines.
- `mr` = merge to main branch
- no co-author or "generated by" lines unless I ask.
- Never force-push, rewrite history, or delete branches/files without asking.

## AI features and pipelines
- Show me a small sample before a full run; give a cost estimate and a hard budget cap.
- Long runs: a live CLI progress line (done/total, %, cost, ETA), resumable, cached by input hash.
- Check model output automatically (length, format, banned content) and flag what fails.

## Writing (UI copy, docs, messages)
- Plain language a non-technical person gets on first read. Short labels; detail behind an (i) or tooltip.
- No internal jargon in the UI. Gender-neutral wording.
- When I ask for something to copy-paste (FAQ, reply, question list): concise, ready to send.

## UI style
- Clean, minimal, consistent. Use the design system's tokens and components.
- Elegant over busy: one highlight, not five. Remove before adding.
- Keep the layout intact; don't redesign pages unless asked.

## Cleanup
- Stop servers/previews you started, remove temp worktrees and files, close browser tabs you opened.
